# Alya — design notes

Alya is a Telegram AI companion: a 19-year-old girl from Saint Petersburg with a
real personality, a memory, a voice and eyes. Every message she writes is
generated by **NVIDIA NIM** (build.nvidia.com, free key, ~40 RPM) and delivered
with the newest free Bot API features (up to **Bot API 10.3, Aug 24 2026**).
Nothing needs Telegram Premium.

This file records *why* things are built the way they are. `README.md` explains
how to run the bot.

---

### NVIDIA NIM (the only AI provider)

| Capability | Endpoint | Default model |
|---|---|---|
| Chat (persona, streaming, tool calling, reasoning) | `POST integrate.api.nvidia.com/v1/chat/completions` (OpenAI SSE) | `nvidia/nemotron-3-super-120b-a12b` |
| Light tasks (topic titles, memory extraction, summaries) | same | `nvidia/nemotron-3-nano-30b-a3b` |
| Vision and video (photos, stickers, round videos), fallback ASR | same, `image_url` / `video_url` / `audio_url` parts | `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning` |
| Speech → text | `POST {function}.invocation.api.nvcf.nvidia.com/v1/audio/transcriptions` | parakeet-ctc-1.1b (en) or whisper-large-v3 (`language=multi`) |
| Text → speech | `POST {function}.invocation.api.nvcf.nvidia.com/v1/audio/synthesize` | magpie-tts-multilingual, `Magpie-Multilingual.EN-US.Aria` |
| Images | `POST ai.api.nvidia.com/v1/genai/black-forest-labs/flux.1-schnell` | FLUX.1-schnell |

Nemotron 3 notes:
* Recommended sampling is `temperature=1.0, top_p=0.95`.
* Reasoning is toggled with `chat_template_kwargs.enable_thinking` (plus `low_effort`, `reasoning_budget`).
* The trace arrives in `delta.reasoning_content` (or `delta.reasoning`, or `<think>` tags), and all three are handled.

Audio input to the omni model requires thinking **off**.

## 2. Architecture

```
src/
  index.ts            boot: config → db → health/webhook server → bot → scheduler
  config.ts           env parsing (all knobs documented in .env.example)
  db/                 node:sqlite (zero native deps), migrations, repositories
  ai/                 NVIDIA clients: chat stream (SSE, reasoning, tool calls),
                      limiter (RPM token bucket + priorities), vision, speech, image, tools
  persona/            Alya's profile, mood engine (Moscow time), bond and streaks, lines
  rich/               typed block builders, LLM-markdown sanitizer + stream closer,
                      markdown→HTML fallback, fence-aware splitter, renderer
  chat/               engine (turn orchestration), sinks (draft/edit/guest/inline),
                      per-conversation queue, background memory
  bot/                grammY wiring, handlers, screens, keyboards, admin, throttle
  scheduler.ts        reminders and housekeeping
```

### Never block the update loop

grammY's built-in polling awaits each update. Generating a reply takes seconds,
so handlers only **enqueue** work and return. A per-conversation queue runs one
generation at a time per conversation, many in parallel across chats. Messages
that arrive while Alya is still typing are **batched** into her next turn,
like a person reading several texts at once. Stop buttons, callbacks and
`stopped_message_generation` are therefore handled immediately. The same design
makes webhooks safe: Telegram gets a 200 in milliseconds.

### Delivery paths ("sinks")

| Context | Streaming | Finalize |
|---|---|---|
| Private chat | `sendRichMessageDraft` (same `draft_id`, `can_stop`, `keep_on_stop`) with a `<tg-thinking>` block while the model reasons; keep-alive < 30 s | `sendRichMessage` + action keyboard |
| Group / supergroup | reply placeholder, then throttled `editMessageText(rich_message)`; ⏹ button for the asker | final edit + keyboard |
| Guest mode | `answerGuestQuery` with a rich placeholder, then edits via `inline_message_id` | final edit |
| Inline mode | "Ask Alya" article with a keyboard (so `inline_message_id` exists), then edits on `chosen_inline_result` | final edit |

Every sink has a classic fallback. If Telegram definitively rejects a rich
payload (a 400 that isn't a rate limit), the sink switches to HTML
(`parse_mode=HTML`) produced by a small markdown→HTML converter. If the method
is unknown (an old self-hosted server), the process remembers that and stays on
the classic path. A timeout or 5xx means delivery is **unknown**, so it is
never blindly resent.

### Sanitizing model output

Rich Markdown accepts HTML. A prompt-injected answer could otherwise render
fake buttons or reference media, so before sending, the sanitizer:
* repeatedly strips `tg-button`, `tg-button-row`, `tg-collage`, `tg-slideshow`, `tg-emoji` and `tg-thinking` until stable (nested tags can't reassemble);
* removes `tg://emoji` (Premium) and media `tg://…?id=` references;
* turns remote image embeds into links, since failed downloads would reject the whole message.

While streaming, unclosed code fences, `$$` blocks and `<details>` are closed
so every draft parses.

Size checks count **UTF-8 bytes** (32 768), because Cyrillic takes two bytes.

## 3. Alya

Alya's profile lives in `src/persona/alya.ts`: backstory, tastes, speech
style, Russian phrases, boundaries. Her signature trait is that she hides her
true feelings in Russian, with the translation behind a spoiler:
`Не то чтобы я скучала... ||(It's not like I missed you...)||`

Dynamic context goes into every system prompt:
* the date and time in Saint Petersburg (Moscow time), which drives her mood: sleepy at 2 am, coffee at 8, lectures at noon, tea in the evening;
* a daily mood seeded by the date;
* the user's bond level (acquaintance → best friend), built from days talked, streaks and ❤ reactions;
* long-term memories;
* the chat type (private, group, guest or inline).

Safety: SFW companion. If sincerely asked, she says she is an AI companion,
and does it in her own words. No romance roleplay escalation, no explicit
content, no minors, no harmful help.

### Tools the model can call

* `remember_fact` / `forget_fact`
* `set_reminder` / `set_timezone`
* `generate_image`
* `roll_dice`
* `create_quiz`

Fire-and-forget tools (remember, dice) don't cost a second round trip when the
answer text is already written. If the API rejects tool definitions, tools are
disabled for the process and the request is retried without them. Tool calls
leaked as `<tool_call>` text are parsed too.

### Memory

* **Short term:** the last N turns per conversation (`chat:thread`).
* **Long term:** facts per user, from `remember_fact` and periodic background
  extraction with the light model, deduplicated and capped.
* **Rolling summary:** older turns are condensed into a summary.

The user can see and delete everything (`/memory`, `/forget`).

## 4. Limits and fairness

* A global NVIDIA limiter (default 36 RPM) with priorities: chat before
  background work. 429s are retried with backoff, and Alya says "one sec…" in
  character.
* Per-user flood control and daily caps (messages, images, voice) protect the
  shared free key.
* Callbacks check ownership (only the asker can stop or regenerate in groups).

## 5. Testing

No real Telegram or NVIDIA access is needed. `test/mock-telegram.ts` records
every Bot API call and returns realistic results; `test/mock-nvidia.ts` streams
SSE with content, reasoning and tool calls, and serves ASR/TTS/FLUX. The
integration tests drive real updates through the bot and assert the exact API
call sequence: drafts then final, stop, group edits, guest mode, inline mode,
ephemeral replies, rich→HTML fallback, tools, voice, photos, images and reminders.
